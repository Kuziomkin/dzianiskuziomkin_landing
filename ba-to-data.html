① Start here — your core strength

BA Artifacts

This is your home territory — but the artifacts have different shapes in data projects than in process or requirements work.

  • Source Mappings — document exactly where each field in the target system comes from: source table, transformation logic, business rules. Often the most critical BA deliverable in a data project.
  • Data Flow Diagrams — show how data moves between systems, pipelines, and storage layers. Give developers and architects a shared picture of the data landscape.
  • Data Catalog — a searchable inventory of all data assets: tables, fields, owners, freshness, usage. Think of it as the data equivalent of a requirements register.
  • Data Dictionary — defines what each field means in business terms: business definition, valid values, owner. Without this, different teams use the same field to mean different things.
  • Data Lineage — documents where a piece of data was born, how it was transformed, and where it ends up. Critical for debugging data quality issues and for regulatory compliance.
  • C / L / P Data Models — Conceptual defines business entities and relationships, Logical adds attributes and data types, Physical translates into actual database tables and constraints. As a BA you'll own the conceptual layer and collaborate on the logical one.
  • Data Acceptance Criteria — BAs already write acceptance criteria; in data projects these directly become data quality rules and dbt test conditions. Documenting what "valid" means for each field is one of the most concrete bridges between BA work and data engineering.
② Learn this first

SQL & Analytics

You don't need to become a data engineer. But you do need to be able to query data yourself — otherwise you're dependent on someone else to answer every question.

  • SQL Fundamentals — SELECT, WHERE, GROUP BY, ORDER BY, basic filtering. If you already know this, you're not starting from zero.
  • Joins & Aggregations — where most real analysis happens. Understanding joins deeply (not just knowing they exist) is what lets you trace data across tables and validate source mappings.
  • Window Functions — calculate running totals, rankings, and moving averages without collapsing your data. The difference between answering "total sales this month" vs "each customer's rank within their region over time."
  • CTEs — Common Table Expressions make complex queries readable by breaking them into named steps. How data engineers structure SQL — learning to read and write them makes collaboration much easier.
  • Power BI / Tableau — the most common BI tools you'll encounter. You don't need to master both, but knowing how to build a basic dashboard and read the underlying data model is genuinely useful.
  • Python (Pandas + Jupyter) — specifically pandas for data manipulation and reshaping, and Jupyter notebooks for running and sharing analysis. Being able to load a dataframe, inspect it, and write a simple transformation puts you in a much stronger position when working alongside engineers.
  • Statistical Thinking — SQL tells you what the data says; statistics tells you what it means. Distributions, percentiles, and basic hypothesis testing prevent you from reporting a difference that is just noise. An analyst who understands when a result is statistically meaningful earns significantly more trust from stakeholders.
③ Set up your sandbox — don't leave this until last

Data Platforms

You need a platform to practice SQL, run dbt, and build your portfolio. Don't wait until you've "learned everything else" — open a free account on the same week you start learning SQL. Snowflake has a 30-day free trial with sample datasets included. That's your sandbox. The platform choice matters less than getting one running early.

  • Snowflake — cloud-native, fully SQL-based, and the easiest starting point for analysts. Free trial, sample datasets built in, no infrastructure to manage. Open an account this week and use it as your SQL practice environment.
  • Databricks — built on Apache Spark, leans toward engineering and machine learning workloads. You'll encounter it more in data-heavy or ML-focused teams.
  • MS Synapse — Microsoft's integrated analytics service. Common in enterprises already using the Azure ecosystem. If your client is in Azure, you'll likely meet Synapse.
  • BigQuery — Google's equivalent: serverless, fast, deeply integrated with Google Cloud. Worth knowing even if you don't use it day one.
  • Cloud basics (AWS / Azure / GCP) — understanding that all these platforms live somewhere, and that storage, compute, and networking costs are real things your team cares about.
  • Git basics — not technically a platform, but you need this to use dbt, share SQL scripts, and work in any modern analytics team. Learn commit, branch, and pull request. Takes a weekend, pays back immediately.
④ Foundational

Data Formats & Storage

Before you can work with data, you need to understand what shape it comes in and where it lives.

  • Structured data — rows and columns, like a spreadsheet or SQL table. What most BAs already know. Clean, predictable, easy to query.
  • Semi-structured (JSON, Parquet) — some structure, more flexible. JSON is what APIs return. Parquet is a columnar file format optimized for analytics, widely used in data lakes.
  • Unstructured data — no predefined schema: documents, emails, logs, images. Hardest to work with but increasingly common in data projects.
  • Databases (OLTP / OLAP) — OLTP handles live operational data (CRM, ERP, order systems). OLAP is optimized for querying large historical datasets — the warehouse side. Understanding this distinction helps you ask better questions about data sources.
  • Lakehouses (Delta, Iceberg) — combine the flexibility of a data lake with the structure of a warehouse. Delta Lake and Apache Iceberg are the two dominant open formats you'll hear often in modern architectures.
  • Object Storage (S3, Blob) — where raw files live before they're processed. Think of it as a giant cheap hard drive in the cloud. Data almost always passes through here at some point.
⑤ Design skills

Data Modeling

This is where your BA background gives you the most leverage. Data modeling is fundamentally about understanding business entities and their relationships — exactly what you've been doing with ERDs and process flows.

  • Normalized vs Denormalized — the foundational design choice. Normalized models eliminate redundancy (good for operational databases). Denormalized models flatten data for faster analytics queries (good for warehouses). Knowing when to use which is one of the most valuable things a BA can contribute.
  • Star Schema — the most common warehouse pattern: one central fact table surrounded by dimension tables. Simple, fast, easy to understand. Most BI tools are optimized for it.
  • Snowflake Schema — a normalized version of the star where dimensions are broken into sub-dimensions. More flexible, slightly more complex to query.
  • Dimensional Modeling — the formal methodology behind star schemas (Ralph Kimball). Gives you a vocabulary and design principles for building warehouses business users can actually understand.
  • Data Vault — an alternative modeling approach designed for auditability and scalability. Common in financial services and large enterprises. You won't design one as a BA, but you'll encounter the terminology.
  • SCD Types (1 / 2 / 3) — Slowly Changing Dimensions describe how to handle source data that changes over time. Type 1 overwrites the old value. Type 2 adds a new row and keeps full history. Type 3 adds a "previous value" column. Understanding the difference matters every time a source mapping needs to answer "as of" questions or track customer history — which is constantly.
⑥ Pipeline thinking

ETL & ELT

This is about understanding how data moves from source systems into your warehouse — and who does the work of transforming it.

  • ETL vs ELT — ETL transforms data before it lands in the warehouse. ELT loads raw data first, then transforms it inside the warehouse using SQL. Modern stacks have largely shifted to ELT because storage is cheap and warehouse compute is powerful.
  • dbt — the most widely used tool for the Transform step in ELT. Lets data teams write modular, version-controlled SQL transformations. You probably won't write dbt as a BA, but you'll reference its models when documenting lineage and data flow.
  • Azure Data Factory — Microsoft's managed pipeline service. Extracts data from sources, moves it, and schedules runs. Common in Azure-heavy environments.
  • Airbyte / Fivetran — connectors that handle Extract and Load automatically, syncing SaaS tools (Salesforce, HubSpot, Stripe) into your warehouse without custom code.
  • Airflow — an orchestration tool that schedules and monitors pipelines. Think of it as the manager that makes sure everything runs in the right order at the right time.
  • Data Quality & Testing — dbt tests (not_null, unique, accepted_values, referential integrity) and tools like Great Expectations enforce that pipelines don't silently produce bad data. A pipeline without tests is a pipeline no one trusts. Your acceptance criteria from the requirements phase become the test cases here.
